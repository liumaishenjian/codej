- Team Board、跨进程订阅、peer messaging、lease 与自动领取延期 `SUB-11`。

结论：Accepted。

## G2：研究与 ADR

- ADR-088 冻结 root-owned Board、单向 canonical `blockedBy`、派生 `blocks/blocked/recoveryRequired`、revision/tombstone、claim 与幂等契约。
- 四个 Tool 采用独立 snake_case schema，只能经过唯一 `ToolExecutionPipeline`；Permission 仅放行精确 BUILT_IN name/effect 组合。

- Ink 只消费事件和快照，不取得 Task 执行权，也不修改 canonical final。

## 2026-08-27 第九次 corrective：Plan/Task 生命周期确定性收敛

真实用户运行再次证伪“模型应维护 Task、未维护时只显示 advisory”这一假设：五步中文 Plan 可在 Task Board 为空或仅含“制定计划”元任务时进入审批，批准后又可能创建翻译/汇总第二 identity；即使 Evidence 已满足，原 Task 未逐项完成时 final prose 仍可能被接受。授权快照复核继续确认 Plan Mode 使用普通 TaskCreate/Update/List/Get，批准工件不从 Markdown 重建 Task；本项目因此没有恢复 seeder 或标题匹配，而是独立加入三道宿主确定性保证：

1. 宿主在 Plan planning/execution 的 `task_create` 前注入模型不可提交的 `codej.plan_id` metadata；`request_plan_review` 只检查当前 planId cohort，并要求至少一个 bound incomplete Task。普通 Run 或旧 Plan 的 pending Task 保留在同一 Session Board，但既不能满足也不能阻断 review。成功 `WRITE_SESSION_STATE` mutation 精确释放 readiness fingerprint，使相同 review 参数可重试，且不会清除 Permission/HTTP 等无关失败。
2. Planning/approved execution 每个模型回合都只投影当前 planId cohort 的最多 25 项权威摘要，要求一次 claim 一个可运行 Task、验证后立即 complete；不从 Markdown 或 Task 标题推断语义。曾加入的中英文 meta-task 关键词正则已移除，因为它会误拒绝合法的“开发规划模块”任务，且不是授权源码机制。
3. `PlanExecutionCorrectionController` 每次候选 final 同时验证 Evidence 与当前 planId cohort 未完成 Task；两者都收敛才 ACCEPT。历史无关 Task 不进入 reminder、correction 或 final Gate。Task-only correction 通过 lifecycle/stdio strict payload 投影 `incompleteTaskCount/incompleteTaskIds`；达到重复指纹或两次上限而当前 cohort 仍未完成时 REJECT final，不能伪造 Run/Plan 成功，也不自动重放旧副作用。
