## 一、目标与完成定义

最终要形成一条可真实验收的闭环：

```text
输入任务
→ 模型回答
→ 工具调用
→ 审批或提问
→ 实际修改
→ 落盘后重新读取核验
→ 最终回答与真实产物
→ 可以继续下一轮
```

完成不能由测试数量或界面“看起来像”推导。只有以下条件同时满足，核心重构才算完成：

1. 普通对话、工具调用、审批、问卷和 `/plan` 都使用真实 Java Runtime、stdio 和 Tool Pipeline。
2. 文件修改和创建能展示真实结果，并完成落盘后核验。
3. 计划能走完“任务描述 → 可审核计划 → 确认 → 实际执行 → 真实产物 → 最终正文”。
4. 失败、取消、拒绝、冲突、断连和迟到事件不会伪造成功或重新激活旧操作。
5. 用户可见交互逐项有参考源码调用链或已确认需求依据；没有依据的提示、面板和流水不得新增。
6. 真实入口 `codej --tui-next` 完成 Windows PTY 验收，离线 `preview:tui` 继续保留为视觉演示。

本项目仍保持独立 Java/TypeScript 重实现，不复制参考源码函数体、Prompt、私有命名、文案、文件布局或实现常量。

## 三、分批执行任务

### 任务 1：落盘后重新读取核验

**范围**：`CLI-04/05/09`、`TOOL-10/11`，当前等级不提升。  
**参考入口**：

- `src/tools/FileWriteTool/FileWriteTool.ts`
- `src/tools/FileWriteTool/UI.tsx`
- `src/tools/FileEditTool/UI.tsx`
- `src/tools/FileEditTool/utils.ts`

**实现内容**：

1. `apply_patch` 成功后在同一安全边界内重新读取目标文件。
2. `write_file` 成功后重新读取新文件。
3. 对比实际内容与预期结果，输出结构化核验状态。
4. TUI 明确显示：
   - 已写入并核验；
   - 工具成功但核验失败；
   - 文件冲突；
   - 被拒绝；
   - 内容被脱敏。
5. 审批前预览继续标记为“修改意图”，不能称为实际磁盘 diff。
6. 重新读取失败时保留失败事实，不根据预览猜测成功。

**验收场景**：

- 正常修改后显示真实相对路径和核验成功。
- 审批后由外部进程修改文件，显示冲突或核验失败。
- 创建文件后独立读取内容与工具结果一致。
- 拒绝、取消、敏感文件和路径逃逸均不显示成功。

### 任务 2：`/plan` 执行闭环

**范围**：`PLAN-01`、`CLI-04/05/09`、`TOOL-10/11`，保持当前等级。  
**参考入口**：

- `src/commands/plan/plan.tsx`
- `src/tools/ExitPlanModeTool/`
- `src/tools/ExitPlanModeTool/UI.tsx`

**实现内容**：

1. 支持 `/plan 任务描述` 直接进入规划。
2. 支持无参 `/plan` 进入或查看当前计划。
3. 计划展示后提供确认执行、提出修改意见、取消。
4. 确认后沿用现有原子审核接口和人工审批。
5. 执行完成后必须进行实际文件核验并返回最终正文。
6. 计划执行失败时停止，不显示任务完成。
7. 修改意见回到同一计划上下文，保留必要上下文。
8. 计划验收失败时不能只留下任务状态更新，必须说明未完成交付。
9. 工具参数无效时进入可恢复的模型纠正流程，不产生伪成功。

**明确不增加**：`/plan-*` 命令族、计划恢复/重试命令、步骤管理命令、后台任务管理。

**验收场景**：

```text
任务描述
→ 计划生成
→ 用户确认
→ 工具审批
→ 实际修改
→ 真实核验
→ 最终正文和产物路径
→ 下一轮输入
```

### 任务 3：工具结果与最终交付统一

**范围**：`CLI-04/05/09`、`TOOL-10/11`。  
**参考入口**：

- `src/components/messages/GroupedToolUseContent.tsx`
- `src/components/messages/UserToolResultMessage/`
- `src/tools/AgentTool/UI.tsx`

**实现内容**：

2. 默认视图只显示摘要，Ctrl+O 显示真实参数和完整有界输出。

4. 同回合同类搜索继续合并，失败调用仍单独可见。
5. 内部工具默认隐藏；失败时保留必要诊断。
6. 迟到事件不能覆盖终态或重新打开审批。
7. 工具前说明、任务更新和审批成功不能冒充最终正文。

**验收场景**：

- 工具失败时界面显示失败，不能显示完成。

## 四、执行顺序和停止条件

执行顺序固定为：

```text
任务1 落盘核验
→ 任务2 /plan闭环
→ 任务3 结果交付
→ 任务4 审批问卷
→ 任务5 视觉交互
→ 任务6 长输出阅读

```

每个任务完成后先跑对应自动测试和最小真实场景，再进入下一任务。发现前一任务未满足终态时，先修复，不跳到后续视觉扩展。

当账户额度剩余 1% 时立即停止代码修改、测试和后台运行，只保留当前工作树状态与已生成证据，不自动提交或推送。

### 2026-10-06 复验边界

- TUI 生产构建通过，标准 TUI 回归为 30 个测试文件、449 passed / 7 skipped；模型适配器、计划组合和 Runtime 定向回归仍以本文件和 S15 证据中的既有结果为准。
- 使用仓库规定的 `cc-java-cli/target/test-dependency-classpath.txt` 后，真实 Java→stdio→Ink 复验能够区分两类问题：把仓库根目录 JUnit-only classpath 当作运行时 classpath 会在启动前缺少 Jackson；修正 classpath 后，1/6 初始化场景通过，另外 5/6 在 Java 启动前被临时 `provider/home/.cc-java` 的 Windows ACL 拒绝。该环境错误不计为业务失败，也不能作为成功 Provider 证据。
- 随后修正确定性 Fixture 启动器：父目录放在仓库 `target/.tui-real-java-fixtures`，Java 进程显式使用当前 OS 账户名。当前完整跨进程复验为 4/6 通过（计划、验证恢复、Task Board、审批会话）；剩余 XLSX `run_command` 和命令超时场景已进入真实工具执行，但 Java `ProcessBuilder` 启动固定 Windows PowerShell 返回 `CreateProcess error=5`，投影为 `execution_failed`。这两个场景不计为业务通过，也不通过修改生产 Shell 安全边界规避。
- 将工作区放到 `target/real-provider-workspace-*`、用户目录放到隔离的 `target/real-provider-home-*` 后，Java stdio 初始化可完成，真实入口能安全投影 `model_retry_exhausted`/`provider_error`，没有工具调用、文件副作用或伪成功；本地 dummy endpoint 探针也只验证了初始化、运行开始和安全失败事件。
- 仓库工作区直接作为 Session Store 外层时，Runtime 按既有安全契约拒绝启动（`Session Store root 必须位于 Workspace 外`）；这不是通过修改产品安全边界来“修复”的启动错误。
